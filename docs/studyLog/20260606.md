# 2026-06-06

## 두 장바구니를 나란히 놓고 본 것

오늘은 우테코 미션으로 만든 풀스택 장바구니(shopping-cart-full-stack)를 다시 열어보고, 지금 SEED로 다시 만들고 있는 장바구니와 나란히 비교했다. 같은 화면을 두 번 만든 셈인데(어떻게 보면 총 세 번), 두 구현이 무엇을 가지고 있고 무엇이 빠져 있는지를 맞대어 보니 디자인 시스템을 쓴다는 게 실제로 무슨 의미인지가 또렷해졌다.

미션 쪽은 풀스택이라 서버와 통신하는 흐름이 있다 보니 자연스럽게 로딩 상태, 에러와 재시도, 낙관적 업데이트가 들어가 있었다. CartContainer 하나만 봐도 isLoading이면 Spinner를, error면 ErrorMessage를 보여주고, useOptimistic과 useTransition으로 수량 변경이나 삭제를 화면에 먼저 반영한 뒤 서버 응답을 기다린다. 무료배송까지 얼마 남았는지 알려주는 FreeShippingNotice도 있고, 주문을 확인하는 별도 페이지도 라우팅으로 분리돼 있었다.

반대로 SEED로 만든 쪽은 정적인 mockData를 useState에 올려두고 시작하는 구조라 그런 비동기적 상태들은 아예 없었다. 대신 미션에는 없던 것들이 있었다. 삭제할 때 그냥 사라지는 게 아니라 AlertDialog로 "상품을 삭제할까요?"를 한 번 묻고, 전체선택 체크박스는 indeterminate로 일부만 선택된 상태를 표현하며, 이미지는 ImageFrame이 비율 고정과 실패 시 fallback까지 처리한다. 같은 장바구니인데 한쪽은 데이터 흐름이 촘촘하고 다른 한쪽은 화면 처리가 촘촘했다.

이 대비가 오늘의 출발점이었다. 두 구현의 장점을 합치되, 비동기 흐름까지 흉내 내는 건 이번 범위에서 빼기로 했다. 정적 데이터는 그대로 두고, 미션에는 있지만 SEED 프로젝트에는 빠져 있던 UX들을 SEED 컴포넌트로 채우는 데 집중했다. 학습의 목적이 풀스택 재현이 아니라 "이 UX를 SEED의 어떤 컴포넌트가 담당하는가"를 손으로 익히는 것이었기 때문이다.

## 컴포넌트가 두 층으로 나뉘어 있다는 것

작업을 시작하면서 처음 막힌 지점이 의외의 곳이었다. Snackbar, Callout, BottomSheet를 쓰려고 공식 문서를 봤더니, import 경로가 `@seed-design/react`가 아니라 `seed-design/ui/snackbar`처럼 내 프로젝트 안의 스니펫을 가리키고 있었다. 처음엔 패키지에서 바로 가져다 쓰면 되는 줄 알고 패키지 export부터 뒤졌는데, Callout이나 BottomSheet가 거기 분명히 있긴 했다. 그런데 그건 저수준 조각들이었다.

알고 보니 SEED는 같은 컴포넌트를 두 층으로 제공하고 있었다. 아래층은 `@seed-design/react`에 들어 있는 원시 부품들로, Callout.Root, Callout.Content, Callout.Description처럼 잘게 쪼개진 compound 형태다. 위층은 그 부품들을 엮어서 description과 tone 같은 간단한 props만으로 쓸 수 있게 감싼 스니펫이다. 권장되는 건 위층, 즉 스니펫을 CLI로 설치해서 쓰는 방식이었다. 이미 프로젝트에 들어와 있던 action-button이나 alert-dialog도 전부 이 스니펫 층이었다.

왜 이렇게 두 층으로 나눠뒀을까를 생각해봤다. 저수준 부품만 주면 모든 사람이 매번 Root와 Content와 Description을 직접 조립해야 하고, 그 과정에서 누구는 빠뜨리고 누구는 순서를 틀린다. 바로 6월 3일에 겪었던 Checkbox.HiddenInput 누락 버그가 그 위험의 전형이었다. 그렇다고 완성된 컴포넌트만 패키지로 박아주면 내부를 고칠 수가 없다. 스니펫은 그 사이의 절충이다. 자주 쓰는 조합을 미리 엮어서 내 프로젝트에 복사해주되, 그 코드가 내 것이라 언제든 뜯어고칠 수 있다. 결국 첫날에 정리했던 "스니펫 방식은 커플링을 끊는다"는 이야기가, 단순히 버전 독립성만이 아니라 조립의 안전성까지 포함하는 것이었다는 걸 오늘 다시 확인하였다.

그래서 snackbar, callout, bottom-sheet 세 개를 CLI로 설치했다. 설치하면서 아이콘 의존성 하나가 같이 딸려 내려오는 것도 봤는데, 첫날 MannerTemp가 유틸 파일까지 함께 내려온 것과 같은 방식이었다.

## 스낵바는 화면에 두는 게 아니라 호출하는 것

Snackbar를 붙이면서 가장 새로웠던 건 사용하는 방식 자체였다. 지금까지 다룬 컴포넌트는 전부 JSX 어딘가에 자리를 잡고 props로 상태를 받았는데, 스낵바는 그렇지 않았다. 앱 최상단을 SnackbarProvider로 감싸두면, 그 안에서 useSnackbarAdapter로 adapter를 받아 필요한 순간에 adapter.create를 호출하는 명령형 방식이었다.

```tsx
snackbar.create({
  render: () => (
    <Snackbar
      message="상품을 삭제했어요"
      actionLabel="실행취소"
      onAction={() => restoreItem(snapshot)}
    />
  ),
});
```

처음엔 이게 왜 다른 컴포넌트들과 다르게 생겼는지 의아했는데, 스낵바의 성격을 생각하니 납득이 갔다. 스낵바는 특정 위치에 항상 떠 있는 요소가 아니라, 어떤 행동의 결과로 잠깐 나타났다 사라지는 알림이다. 그걸 JSX 트리 안에 두려면 "지금 스낵바가 떠 있는가", "메시지는 무엇인가" 같은 상태를 내가 직접 들고 있어야 하고, 그 상태를 여러 화면이 공유해야 한다. 차라리 Provider가 그 표시 영역과 생명주기를 전부 책임지고, 나는 "이 메시지를 띄워줘"라고 호출만 하는 편이 훨씬 깔끔하다. SnackbarProvider 안을 보니 실제로 Region과 Renderer를 품고 있어서, 어디서 호출하든 화면의 정해진 자리에 알림이 뜨도록 돼 있었다.

## 실행취소는 디자인 시스템이 주지 않는다

스낵바에 실행취소 버튼을 달면서 한 가지를 분명히 깨달았다. SEED가 주는 건 "실행취소"라는 글자가 붙은 버튼과 그걸 누를 수 있는 자리까지다. 실제로 삭제한 항목을 되살리는 일은 온전히 내 몫이었다.

원래 removeItem은 그냥 해당 아이템을 목록에서 걸러내고 선택 집합에서 빼는 게 전부였다. 그런데 되돌리려면 무엇을 지웠는지, 어디에 있었는지, 그게 선택된 상태였는지를 기억해야 한다. 그래서 removeItem이 삭제하기 직전에 그 정보를 스냅샷으로 묶어 반환하도록 바꿨다.

```ts
function removeItem(id: number): RemovedSnapshot | null {
  const index = items.findIndex((item) => item.id === id);
  if (index === -1) return null;
  const removed = items[index];
  const wasSelected = selected.has(id);
  // ...목록과 선택에서 제거...
  return { item: removed, index, wasSelected };
}

function restoreItem({ item, index, wasSelected }: RemovedSnapshot) {
  setItems((prev) => {
    const next = [...prev];
    next.splice(index, 0, item);
    return next;
  });
  if (wasSelected) {
    setSelected((prev) => new Set(prev).add(item.id));
  }
}
```

restoreItem이 splice로 원래 인덱스에 다시 끼워넣는 게 핵심이었다. 그냥 배열 끝에 다시 붙이면 되살아나긴 해도 순서가 바뀌어버린다. 실행취소라는 건 시간을 되감는 일이니 위치까지 정확히 돌아와야 사용자가 어색함을 느끼지 않는다. 선택 상태도 마찬가지여서, 지우기 전에 체크돼 있었으면 복원할 때도 체크된 채로 돌아와야 한다.

이 작업을 하면서 디자인 시스템과 도메인 로직의 경계가 어디인지가 손에 잡혔다. 첫날부터 "컴포넌트는 결정을 내리지 않고 앱에 맡긴다"는 SEED의 철학을 여러 번 정리했는데, 그게 추상적인 원칙이 아니라 실제로 이런 모양이라는 걸 오늘 직접 겪었다. SEED는 알림을 띄우는 그릇과 버튼을 주고, 그 버튼이 눌렸을 때 무엇을 되돌릴지는 내가 채운다. 무료배송 안내도 똑같았다. Callout은 tone에 따라 색과 모양만 정해주고, "얼마가 남았는지", "지금이 무료배송 대상인지"를 판단하는 계산은 useCart 안의 내 로직이 한다.

## 분석만 했던 BottomSheet를 실제로 써보다

6월 3일에 BottomSheet의 handleOnly나 onOpenChange가 닫힌 이유를 구분해 전달하는 설계를 소스코드만 보고 분석했었는데, 오늘은 그걸 실제로 주문 확인 화면에 붙여봤다. 미션에서는 주문 확인이 라우팅으로 분리된 별도 페이지였지만, SEED 쪽에서는 같은 화면에서 시트가 올라오는 방식으로 만들기로 했다. 당근 앱에서 흔히 보는 그 동작이고, 라우터를 끌어들이지 않아도 된다는 점도 좋았다.

붙이다가 한 가지 걸린 게 있었다. 시트 안의 푸터에 둔 "결제하기" 버튼을 눌러도 시트가 저절로 닫히지 않았다. 문서를 보니 푸터 버튼은 자동으로 닫는 동작이 없고, 닫는 건 기본 닫기 버튼이나 바깥 클릭, 아래로 드래그가 담당한다고 돼 있었다. 그래서 BottomSheetRoot를 open과 onOpenChange로 제어하는 형태로 바꿔서, 결제하기를 누르면 내가 직접 open을 false로 내리고 곧바로 "주문이 완료되었어요" 스낵바를 띄우도록 연결했다.

이것도 결국 같은 결의 이야기였다. 시트를 닫는 건 시각적 동작이지만 "결제하기를 눌렀으니 닫는다"는 건 흐름에 대한 판단이고, 그 판단은 컴포넌트가 아니라 내가 한다. 6월 3일에 BottomSheet가 닫힌 이유를 drag인지 closeButton인지 구분해서 넘긴다고 분석했던 게, 바로 이렇게 닫는 주체와 시점을 앱이 통제할 수 있도록 열어둔 설계의 연장선이라는 걸 직접 만들어보고서야 제대로 이해했다.

## 디자인 시스템에도 빈자리가 있다

작업하면서 SEED가 모든 걸 다 주지는 않는다는 것도 알게 되었다. 수량을 올리고 내리는 +/- 컨트롤, 그러니까 스텝퍼에 해당하는 컴포넌트가 SEED에는 없었다. 무료배송까지 남은 금액을 막대로 보여주는 선형 ProgressBar도 없었다. 원형인 ProgressCircle만 있었다.

처음엔 이게 빠진 건가 싶었는데, 생각해보면 디자인 시스템이 세상의 모든 UI 조각을 담을 수는 없다. 우선순위가 있고, 당근 앱에서 자주 쓰이지 않는 패턴은 후순위로 밀릴 수밖에 없다. 수량 스텝퍼는 결국 커스텀 버튼으로 남겨두기로 했고, 무료배송은 막대 없이 Callout 텍스트로만 안내하기로 했다. 디자인 시스템을 쓴다는 게 모든 걸 시스템 안에서 해결한다는 뜻은 아니고, 시스템이 주는 것과 내가 직접 채우는 것 사이의 선을 그을 줄 아는 것까지 포함한다는 생각이 들었다.

## 스니펫과 내 도구가 어긋날 때, 다시

설치한 bottom-sheet 스니펫에서 타입 에러가 하나 났다. 스니펫 안에서 개발 환경인지 판별하려고 `process.env.NODE_ENV`를 쓰는데, 이 프로젝트에는 Node 타입이 설치돼 있지 않아서 process를 못 찾는다는 에러였다. 6월 2일에 겪었던, 공식 스니펫이 내 프로젝트의 도구 버전과 어긋나면서 타입 에러가 났던 그 상황과 정확히 같은 종류였다.

그때는 ForwardedRef 캐스팅이 엄격해진 타입 체커 때문이었고 이번엔 Node 타입의 부재 때문이지만, 본질은 똑같다. 스니펫은 어떤 표준적인 환경을 가정하고 작성되는데, 내 프로젝트가 그 가정과 다르면 내 코드를 한 줄도 안 건드려도 에러가 난다. 다른 점이라면 이번엔 그 스니펫 코드가 이미 내 프로젝트 안에 들어와 있어서 직접 고칠 수 있었다는 것이다. 이게 바로 스니펫 방식의 이점이기도 하다. 외부 패키지였다면 이슈를 올리고 기다려야 했겠지만, 내 파일이니 그냥 고치면 된다.

Vite 프로젝트라 `process.env.NODE_ENV` 대신 `import.meta.env.DEV`를 쓰면 Node 타입 없이도 개발 환경을 판별할 수 있어서 그렇게 바꿨다. 타입 체크가 깨끗해졌고, 무엇보다 이 프로젝트의 번들러에 맞는 표현으로 정리되었다는 점이 마음에 들었다. 스니펫은 내려받는 순간 내 코드가 되니, 내 환경에 맞게 다듬는 것까지가 자연스러운 흐름이라는 걸 다시 느꼈다.

## 정리하면서

오늘은 분석에서 한 발 더 나아가 실제로 컴포넌트를 붙이고 동작하게 만드는 날이었다. 그동안 소스코드를 읽으며 "왜 이렇게 설계했을까"를 추측했다면, 오늘은 그 설계를 실제로 써보면서 추측이 맞았는지를 확인하였다. Snackbar가 명령형으로 호출되는 이유, BottomSheet가 닫힘을 앱에 맡기는 이유, Callout이 판단이 아니라 표현만 책임지는 이유가 전부 직접 만들어보고 나서야 머리가 아니라 손으로 이해되었다.

다음에는 이번에 미뤄둔 가짜 비동기 레이어를 붙여보고 싶다. setTimeout으로 로딩과 에러를 흉내 내면 Skeleton으로 로딩을 그리고, Callout으로 에러와 재시도를 안내하고, 낙관적 업데이트까지 미션과 같은 수준으로 재현해볼 수 있을 것이다. 그러면 비동기 흐름 속에서 SEED 컴포넌트들이 어떻게 맞물리는지, 특히 첫날부터 계속 따라다닌 loading과 disabled의 분리가 실제 비동기 상황에서 어떤 차이를 만드는지 직접 확인할 수 있을 것 같다.
