## ForwardedRef 타입 불일치와 오픈소스의 버전 문제

오늘은 `list.tsx` 스니펫 파일을 읽다가 TypeScript 에러를 하나 발견했다. `ListDivider` 컴포넌트 안에서 `ref as React.ForwardedRef<HTMLHRElement>` 라고 타입 캐스팅하는 코드가 있었는데, TypeScript가 이걸 거부하면서 에러 메시지를 뱉어냈다.

에러 내용은 이랬다. `'ForwardedRef<HTMLLIElement>' 형식을 'ForwardedRef<HTMLHRElement>' 형식으로 변환한 작업은 실수일 수 있습니다. 두 형식이 서로 충분히 겹치지 않기 때문입니다.` 처음엔 캐스팅 방식 자체가 잘못된 줄 알았는데, 파악해보니 구조적인 이유가 있었다.

`ListDivider`는 `forwardRef<HTMLLIElement>`로 선언되어 있다. 리스트 안에서 구분선으로 쓰이는 컴포넌트라 `as="li"`를 넘겨서 `<li>` 요소로 렌더링하기 때문이다. 그런데 내부에서 쓰는 `SeedDivider`는 ref 타입이 `HTMLHRElement`로 고정되어 있다. `SeedDivider`가 기본적으로 `<hr>` 요소를 렌더링하는 컴포넌트라 그렇게 설계된 것이다. 결과적으로 `HTMLLIElement` ref를 `HTMLHRElement` ref로 캐스팅하려고 하면 TypeScript가 거부한다. 두 타입은 모두 `HTMLElement`를 상속하지만 서로 고유한 속성을 가지는 형제 타입이라 겹치는 부분이 충분하지 않다.

흥미로운 건 이 코드가 SEED Design 공식 스니펫이라는 점이다. 공식 코드에 타입 에러가 있다는 게 이상하다고 생각했는데, 원인을 찾아보니 오픈소스 주변 도구의 버전업 때문이었다. 스니펫이 작성될 당시의 TypeScript나 `@types/react` 버전에서는 `HTMLLIElement → HTMLHRElement` 단일 캐스팅을 허용했던 것 같다. 그런데 지금 프로젝트는 `@types/react@^19.2.15`를 쓰고 있고, 버전이 올라가면서 타입 체크가 더 엄격해졌다. 내 코드는 하나도 안 건드렸는데 의존성 버전 올리고 나서 타입 에러가 생기는 것과 완전히 같은 맥락이다.

근본 원인이 어디 있는지도 생각해봤다. 스니펫 자체가 아니라 `SeedDivider` 패키지 내부에 있다. `SeedDivider`는 `as` prop을 받아서 렌더링할 HTML 요소를 바꿀 수 있는데, ref 타입이 `as` prop을 따라가지 않고 `HTMLHRElement`로 고정되어 있다. 이 부분을 제대로 타입으로 표현하려면 제네릭이 필요하다.

```ts
type DividerProps<T extends React.ElementType = 'hr'> = {
  as?: T;
  ref?: React.Ref<React.ElementRef<T>>;
}
```

이런 식으로 `as` prop의 타입에 따라 ref 타입도 동적으로 바뀌게 만들어야 한다. 그런데 이게 라이브러리 내부를 꽤 많이 바꾸는 작업이다 보니, 이슈를 올린다 해도 우선순위가 낮을 가능성이 높다. 특히 SEED Design이 요즘 `as` prop 대신 `asChild` 패턴으로 방향을 잡고 있는 것 같아서, `as` prop 관련 타입 문제를 굳이 고치지 않고 deprecated 처리할 수도 있다.

## 제네릭이 실무에서 쓰이는 맥락

오늘 대화 중에 "실무에서 제네릭 잘 안 쓴다던데"라는 말이 나왔다. 이걸 정리해둘 필요가 있다고 느꼈다.

제네릭을 직접 설계하는 일은 드물다는 말이 맞다. 앱 코드를 짜는 레이어에서는 `useState<User[]>`, `useRef<HTMLButtonElement>`, `axios.get<Response>` 처럼 이미 만들어진 제네릭을 가져다 쓰는 게 대부분이다. `<T extends ...>` 처럼 직접 제네릭 타입 파라미터를 설계하는 경우는 공통 훅이나 유틸 함수를 만들 때 정도다.

그런데 오늘 본 `SeedDivider` 케이스처럼, 라이브러리나 디자인 시스템 코드에서는 제네릭이 핵심 도구다. `as` prop으로 다형성을 지원하는 컴포넌트를 타입 안전하게 만들려면 제네릭 없이는 방법이 없다. Radix UI나 MUI 소스코드를 열어보면 복잡한 제네릭이 가득한 이유다.

결국 "실무에서 잘 안 쓴다"는 말은 앱 레이어 기준이다. 라이브러리를 만드는 사람에게는 제네릭이 매일 쓰는 도구고, 그 라이브러리를 읽고 이해하는 건 어느 레이어에서 일해도 필요하다. 오늘처럼 스니펫 코드를 읽다가 타입 에러를 만났을 때 원인을 파악하려면 제네릭이 어떻게 동작하는지는 알아야 한다.
