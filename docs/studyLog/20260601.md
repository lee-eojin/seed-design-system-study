## 시작하면서

SEED Design을 공부하기로 했다. 2주간 목표는 당근의 디자인 시스템인데 왜 이렇게 설계했는지를 이해하는 게 목표이다. 좋은 디자인 시스템이 어떤 고민에서 만들어지는지 만드는 사람의 시각으로 보고 싶었다.

프로젝트 셋업은 직접 했다. `@seed-design/react`와 `@seed-design/css`를 설치하고, vite.config에 `seedDesignPlugin()`을 등록하고, `main.tsx`에서 `@seed-design/css/base.css`를 불러오는 것까지 하나하나 손으로 맞췄다. 그러다가 Claude Code에 SEED Design 전용 스킬이 있다는 걸 알게 됐고, 그때부터는 스킬을 써서 컴포넌트를 탐색하고 스니펫을 설치하기 시작했다. `action-button`, `loading-indicator`, `progress-circle` 세 개는 그렇게 들어온 것들이다.

## SEED Design만의 특징

SEED Design이 다른 디자인 시스템과 어떻게 다른지 정리를 해보았다.

가장 독특한 점은 스니펫 방식이다. 보통 디자인 시스템 라이브러리는 npm 패키지에서 import해서 쓴다. 그런데 SEED Design은 컴포넌트 소스 파일을 내 프로젝트 안으로 직접 복사해서 쓰는 방식을 취한다. shadcn/ui와 같은 발상이다. 처음엔 왜 이렇게 하는지 의아했는데, 생각해보면 이유가 분명하다. 소스가 내 프로젝트 안에 있으니 어떤 부분이든 마음대로 수정할 수 있고, 라이브러리 버전 업데이트에 끌려다니지 않아도 된다. 외부 패키지에 의존하는 컴포넌트는 라이브러리가 바뀌면 내 코드도 영향을 받는데, 스니펫 방식은 그 커플링을 끊어낸다.

당근이 이 방식을 선택한 이유를 추측해보면, 당근 앱은 지역별, 카테고리별, 실험적 피처별로 컴포넌트를 조금씩 다르게 써야 하는 상황이 많았을 것 같다. 모든 팀이 하나의 패키지를 공유하면 한 팀의 변경이 전체에 영향을 미친다. 스니펫으로 소스를 각 프로젝트에 복사해두면, 공통 기반은 유지하면서도 팀마다 독립적으로 수정할 수 있다. 중앙 집중식 라이브러리의 경직성을 피하면서 디자인 일관성은 챙기는 절충안이라고 생각했다.

`loading`이 `disabled`를 포함하지 않는다는 점도 인상적이었다. 대부분의 디자인 시스템에서 버튼의 loading 상태는 자동으로 비활성화를 포함한다. 사용자가 다시 누르지 못하게 막는 것이다. 그런데 SEED는 이 두 개념을 의도적으로 분리했다. 로딩 중이라는 시각적 피드백을 주면서도 이벤트는 계속 발생할 수 있게 한다. 굳이 왜 분리하나 싶었지만, 실제로 이 둘이 항상 같이 가야 하는 건 아닌 것 같다. 어떤 상황에서는 로딩 중에도 다른 동작을 허용해야 할 수 있다. 그 판단을 컴포넌트가 대신 내리지 않고 사용하는 쪽에 맡기는 설계인 셈이다.

당근 앱의 특성상 이 설계가 더 납득이 갔다. 예를 들어 채팅 전송 버튼을 눌렀을 때 로딩 중에도 다른 메시지를 입력하거나 뒤로 나가는 게 막히면 안 된다. 네이티브 앱에서는 로딩 중에도 사용자가 자유롭게 다른 행동을 할 수 있는 게 자연스럽다. 웹뷰로 네이티브처럼 동작해야 하는 당근 입장에서, loading이 자동으로 disabled를 포함한다면 오히려 어색한 UX가 만들어지는 상황이 자주 생겼을 것이다.

`bleedX`와 `bleedY`라는 props도 눈에 띄었다. Ghost나 Outline 버튼은 내부에 padding이 있기 때문에 텍스트와 시각적으로 딱 맞게 정렬하려면 음수 마진이 필요하다. 보통은 CSS에서 직접 `margin-left: -12px` 같은 식으로 처리하는데, 이걸 props로 끌어올려서 `bleedX="asPadding"`처럼 쓸 수 있게 했다. CSS를 직접 건드리지 않아도 된다는 점에서 일관성이 유지되고, 어떤 의도인지 코드만 봐도 명확하다.

이 props가 있다는 건, 당근 내부에서 Ghost 버튼을 텍스트와 나란히 정렬해야 하는 상황이 꽤 반복됐다는 뜻일 것이다. 매번 CSS로 처리하다 보면 팀마다 다른 값을 쓰게 되고, 결국 화면마다 정렬이 미묘하게 달라진다. 반복되는 패턴을 props로 추상화해서 아예 CSS를 건드릴 필요가 없게 막은 것으로 보인다.

색상도 팔레트 값이 아닌 의미 기반 토큰으로 관리한다. `ScopedColorFg`, `ScopedColorPalette` 같은 이름에서 볼 수 있듯이, 이 색이 어떤 맥락에서 쓰이는지를 이름이 설명한다. 단순히 `blue-500`이 아니라 이 요소가 어떤 역할인지를 색상 토큰 이름으로 표현하는 방식이다.

아마도 당근이 라이트/다크 테마를 지원하면서 이 방식의 필요성이 커졌을 것이다. `blue-500`이라는 팔레트 토큰을 직접 쓰면 다크 모드에서 같은 파란색이 어울리지 않을 수 있다. 반면 "이 색은 주요 액션을 나타내는 색"이라는 의미 토큰을 쓰면, 라이트에서는 `blue-500`, 다크에서는 `blue-300`으로 자동 전환할 수 있다. 색상의 팔레트 값이 아니라 역할을 이름으로 정해두면, 테마가 바뀌어도 코드를 건드릴 필요가 없다.

Stackflow 통합도 특이하다. iOS나 Android처럼 화면이 옆으로 밀리는 네이티브 전환 방식을 웹에서 구현하는 라이브러리인데, SEED Design이 이 Stackflow와 통합된다. 당근마켓 앱이 웹뷰 기반으로 구현된 부분이 많다는 걸 생각하면 납득이 가는 결정이다. 일반 웹 디자인 시스템에서는 보기 어려운 개념이다.

당근 앱 사용자는 당근이 웹뷰인지 네이티브인지 모른다. 그냥 앱으로 쓴다. 화면 전환이 웹의 일반적인 페이드나 점프 방식으로 되어 있으면 사용자가 어색함을 느끼고, 결국 앱 품질이 낮다는 인상을 준다. 디자인 시스템 레벨에서 Stackflow를 통합해두면, 어떤 팀이 어떤 화면을 만들어도 전환 방식이 일관된다. 앱 전체의 사용감을 디자인 시스템이 보장하는 방법으로 받아들였다.

## llms.txt와 컴포넌트 목록

오늘 전체 컴포넌트 목록을 확인하면서 llms.txt라는 것도 처음 알게 되었다. 일반 웹 문서는 HTML로 되어 있어서 광고, 내비게이션, 스타일 코드 같은 불필요한 내용이 뒤섞여 있다. llms.txt는 그 내용을 걷어내고 핵심만 마크다운으로 정리한 파일이다. SEED Design은 공식적으로 이 형식을 지원하고 있어서, AI가 컴포넌트 정보를 정확하게 읽어올 수 있다.

컴포넌트 목록을 보니 생각보다 넓다. 기본 컴포넌트부터 입력 요소, 칩과 탭, 레이아웃 유틸리티, 시트와 다이얼로그, 플로팅 버튼, 피드백 컴포넌트까지 다양하게 있다. 100개가 넘는다고 한다. 특히 `PullToRefresh`나 `ScrollFog` 같은 것들은 모바일 앱에서나 볼 법한 컴포넌트인데 웹에서 지원한다는 점이 흥미로웠다. 당근 앱의 UX를 웹으로 그대로 옮기려는 의도가 보인다.

## MannerTemp로 들여다본 스타일 레이어

오후에는 MannerTemp 컴포넌트를 직접 설치하면서 스타일이 어디서 어떻게 결정되는지 따라가봤다. `npx @seed-design/cli@latest add ui:manner-temp`를 실행했는데 처음에 이름 형식이 달라서 실패했다. `manner-temp`가 아니고 `ui:manner-temp`로 써야 했다. CLI가 친절하게 힌트를 줘서 바로 해결됐다.

설치하고 나니 두 파일이 생겼다. `seed-design/ui/manner-temp.tsx`와 `seed-design/lib/manner-temp-level.ts`이다. 스니펫이 컴포넌트 하나만 설치하는 게 아니라 그 컴포넌트가 의존하는 유틸 파일까지 같이 내려준다는 걸 알게되었다.

`manner-temp-level.ts`를 보니 온도를 레벨로 바꾸는 로직이 담겨 있었다. 경계값 배열을 순회하면서 온도가 어느 구간에 속하는지 찾아내는 방식이다. 36.5도가 기준점(l3)이고, 30도 미만은 l1, 80도 이상은 l10이다. 이 경계값들이 하드코딩되어 있다는 게 처음엔 조금 의아했는데, 생각해보면 매너온도의 레벨 기준은 당근이 정책적으로 결정하는 값이니 굳이 변수로 빼야 할 이유가 없는게 아닐까.

특히, 스타일이 어디서 결정되는지가 가장 궁금했다. `manner-temp.tsx`만 봐서는 알 수 없어서 `node_modules/@seed-design/css` 안을 직접 뒤져봤다. `recipes/manner-temp.css`에 `.seed-manner-temp--level_l1`부터 `l10`까지 클래스가 정의되어 있고, 각 클래스는 `var(--seed-color-manner-temp-l1-text)` 같은 CSS 변수를 참조한다. 그 변수의 실제 색상값은 `base.css`에 모여 있었다. l1은 `#757b85`(회색), l5는 `#ff7300`(주황), l10은 `#cb0123`(빨간)이다. 라이트와 다크 두 가지 값이 모두 정의되어 있어서 테마 전환도 CSS 변수만 교체하면 된다.

정리하면 흐름이 이렇다. 숫자가 들어오면 스니펫의 `mannerTempToLevel`이 레벨로 변환하고, 레벨에 해당하는 CSS 클래스가 붙으면, 그 클래스가 CSS 변수를 참조하고, 변수의 실제 값은 `base.css`에 있다. 컴포넌트 하나를 쓰는데 이렇게 많은 레이어가 관여한다는 게 흥미로웠다. 각 레이어가 자기 역할만 하고 있어서 어느 한 곳을 바꿔도 다른 레이어에 영향이 없는 구조이다.

이 구조를 왜 이렇게 나눴는지 생각해봤다. 만약 색상값이 컴포넌트 코드 안에 직접 박혀 있었다면, 다크 모드를 추가할 때 모든 컴포넌트를 다 뜯어야 한다. CSS 변수 하나만 교체하면 전체가 바뀌는 구조를 만들어두면, 나중에 테마를 추가하거나 색상 정책이 바뀌어도 `base.css` 한 곳만 고치면 된다. 당근이 라이트/다크를 넘어 앞으로 더 다양한 테마를 고려하고 있을 수도 있다고 생각했다.

## TypeScript 유틸리티 타입

스니펫 코드를 읽다 보니 TypeScript 유틸리티 타입을 처음 제대로 이해하게 됐다.

`manner-temp.tsx`에서 `Omit<SeedMannerTempProps, "children" | "asChild">`를 봤다. 처음엔 그냥 뭔가 지우는 거구나 싶었는데, 왜 굳이 이렇게 쓰는지가 궁금했다. 그때그때 필요한 타입을 직접 만들면 안 되나 싶기도 했다.

이유는 유지보수에 있다. `SeedMannerTempProps`에 새 prop이 추가되면, Omit을 쓴 쪽은 자동으로 그 prop을 포함하게 된다. 반면 직접 타입을 정의해뒀다면 라이브러리가 업데이트될 때마다 수동으로 찾아서 추가해야 한다. 외부 라이브러리 타입을 기반으로 래퍼를 만들 때 특히 유용한 패턴이다.

`ElementRef`도 처음 보았다. `React.ElementRef<typeof SomeComponent>`라고 쓰면 그 컴포넌트가 실제로 렌더링하는 DOM 요소의 타입을 추론해준다. `HTMLButtonElement`라고 직접 쓸 수도 있지만, 그러면 나중에 컴포넌트 내부가 바뀌었을 때 타입이 틀려도 모르고 지나갈 수 있다. ElementRef를 쓰면 컴포넌트를 따라 자동으로 바뀐다. Omit과 같은 맥락이다. 원본을 따라가게 만들어서 직접 관리할 포인트를 줄이는 것이다.

## 당근 앱에서 발견한 UX 패턴

당근 앱을 써보다가 글쓰기 버튼이 스크롤을 내리면 "+"로 줄어드는 걸 발견했다. 텍스트와 아이콘이 같이 있는 큰 버튼이 아이콘만 남는 작은 버튼으로 전환되는 거다. 이게 `FloatingActionButton`에서 `ContextualFloatingButton`으로 바뀌는 패턴이라는 걸 알게 됐다.

스크롤 이벤트로 상태를 감지해서 두 컴포넌트를 전환하는 방식이다. 스크롤 전에는 텍스트가 보이는 큰 버튼으로 "지금 쓸 수 있어요"를 알려주고, 스크롤 후에는 공간을 덜 차지하는 작은 버튼으로 줄인다. 콘텐츠를 보는 데 방해가 되지 않으면서도 버튼의 존재를 유지하는 방식이다. 사용자가 위로 스크롤해서 피드 상단으로 돌아오면 다시 큰 버튼이 나타난다.

당근 앱이 웹뷰 기반이라는 걸 생각하면, 이런 패턴을 컴포넌트로 만들어둔 게 납득이 간다. 네이티브 앱에서 흔히 쓰는 UX 패턴을 웹에서도 일관되게 구현하려면 컴포넌트 레벨에서 지원이 되어야 한다. 여러 팀이 각자 스크롤 감지 로직을 구현하면 버튼이 전환되는 시점이나 애니메이션이 제각각이 될 것이다. 이 패턴을 두 컴포넌트의 조합으로 표준화해두면, 어느 화면에서든 같은 감도와 같은 모양으로 동작한다.

## 장바구니 UI를 직접 만들어보면서 배운 컴포넌트 조합 방식

오후 늦게는 실제로 SEED 컴포넌트를 조합해서 장바구니 화면을 만들어봤다. 우테코 미션(장바구니 2단계)을 앞두고, 먼저 SEED를 써보면서 어떻게 컴포넌트를 쪼개고 조합하는지 손으로 익히기 위해서였다. 라이브러리를 import하는 게 미션 규칙상 안 되기 때문에 직접 구현해야 하지만, 설계 방식을 이해하는 데는 SEED를 먼저 써보는 게 훨씬 빠르다고 생각했다.

만들면서 디자인 시스템의 가치를 구체적으로 느꼈다. `Checkbox.Root`에 `indeterminate` prop 하나 넣으면 전체선택의 부분선택 상태가 해결되고, `ImageFrame`은 비율 고정, 테두리, 이미지 로딩 실패 시 fallback까지 다 처리해준다. 내가 직접 구현했다면 체크박스 접근성(aria-checked, indeterminate 상태), 이미지 비율 유지용 padding-bottom 트릭, 깨진 이미지 처리를 전부 손으로 짜야 했을 것이다. 디자인 시스템이 해결하는 게 스타일만이 아니라 이런 세부 UX 처리라는 걸 체감했다.

코드 구조는 세 레이어로 나뉜다. 제일 아래에 SEED의 기본 컴포넌트(`Checkbox`, `ImageFrame`)가 있고, 그 위에 도메인 맥락을 담은 컴포넌트(`CartItem`)가 있고, 제일 위에 페이지(`CartPage`)가 있다. CartItem은 SEED의 Checkbox와 ImageFrame을 직접 import해서 쓰고, CartPage는 CartItem을 쓴다. 페이지는 SEED 컴포넌트를 직접 알지 않아도 된다.

한 가지 헷갈렸던 게 있었다. `import { Checkbox } from "@seed-design/react"` 해놓고 `<Checkbox checked={...} />` 이렇게 쓰려 했는데 타입 에러가 났다. SEED의 Checkbox는 namespace 방식으로 되어 있어서 직접 JSX로 쓸 수 없다. `Checkbox.Root`와 `Checkbox.Control`, `Checkbox.Label`을 각각 조합해야 한다.

```tsx
<Checkbox.Root checked={checked} indeterminate={someChecked} onCheckedChange={toggleAll}>
  <Checkbox.Control />
  <Checkbox.Label>전체선택 ({selected.size}/{items.length})</Checkbox.Label>
</Checkbox.Root>
```

처음엔 번거롭다고 느꼈는데, 이렇게 쪼개놓으면 시각적 요소(Control)와 레이블을 따로 배치할 수 있다. 체크박스 컨트롤만 단독으로 쓸 수도 있고, 레이블 없이 아이콘만 쓸 수도 있다. shadcn/ui나 Radix UI도 같은 방식이다. 당근 앱처럼 다양한 화면에서 체크박스를 쓰다 보면, 어떤 곳은 레이블이 오른쪽, 어떤 곳은 체크박스만 단독으로, 어떤 곳은 리스트 아이템 안에 녹아있는 식으로 쓰임새가 다양할 것이다. 단일 컴포넌트로 모든 케이스를 props로 대응하려 하면 인터페이스가 복잡해진다. 조각으로 쪼개두면 조합이 자유롭다.

상태 관리는 `useCart` 훅 하나에 다 몰아넣었다. 선택된 아이템 목록(`Set<number>`), 수량 변경, 전체선택/해제, 그리고 주문금액과 배송비 계산까지. 배송비 로직은 10만원 이상이면 무료, 아니면 3,000원이다. 이 계산이 컴포넌트 안에 있으면 나중에 로직을 바꿀 때 화면 코드를 뒤져야 한다. 훅으로 분리하면 로직과 뷰가 독립적으로 변경된다.

```ts
const shippingFee = orderAmount === 0 || orderAmount >= FREE_SHIPPING_THRESHOLD ? 0 : SHIPPING_FEE;
```

미션에서 강조하는 "컴포넌트와 비즈니스 로직 분리"가 바로 이 구조다. `CartPage`는 계산된 값만 받아서 보여주고, 계산이 어떻게 되는지는 모른다. `OrderSummary`는 더 단순해서 숫자 세 개를 받아서 표시할 뿐이다.

완성도는 피그마 디자인과 완전히 같지는 않다. 각 아이템에 삭제 버튼이 없고, 빈 장바구니 화면도 없다. 다크모드 배경색도 시스템 설정을 따라가는 바람에 미세하게 달랐다. 하지만 이 구현의 목적이 완성도가 아니라 컴포넌트 조합 방식을 손에 익히는 것이었으니 충분하다. 이제 미션에서는 SEED import 없이, 이 구조 그대로, CSS Module과 직접 구현으로 만들면 된다.

## 앞으로 더 볼 것

오늘은 전체 구조를 훑고, 스타일 레이어를 파고, 직접 화면도 만들어봤다. 다음엔 당근 앱을 더 써보면서 어떤 화면에서 어떤 컴포넌트가 쓰이는지 매핑해볼 계획이다. 앱 UX 패턴을 오늘 하나 발견했는데, 앞으로 더 쓰면서 네 개를 더 찾아야 한다. TypeScript 유틸리티 타입도 오늘 처음 제대로 이해했는데, 다른 스니펫 파일들을 더 읽어보면서 어떤 상황에서 어떤 걸 쓰는지 패턴을 눈에 익혀야 할 것 같다.
