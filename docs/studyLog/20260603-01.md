# 2026-06-03

## 당근 앱에서 찾은 UX 패턴을 가추법으로 뜯어보기

오늘은 SEED Design 컴포넌트들을 단순히 "어떻게 쓰는가"가 아니라 "왜 이렇게 설계됐는가"의 관점으로 분석했다. 접근 방식은 가추법이었다. 소스코드와 props 스펙에서 설계 결정을 관찰하고, 그 결정을 만들어냈을 만한 가설들을 세운 다음, 당근 앱의 실제 사용 맥락에서 어떤 가설이 가장 잘 설명하는지 추론했다.


## loading이 disabled를 포함하지 않는다는 것의 의미

가장 집요하게 파고든 것이 `ReactionButton`이었다. 문서에 이런 문장이 있다. "이벤트 핸들링이 필요할 수 있으므로 loading은 disabled를 포함하지 않습니다." 처음에는 설계 실수를 사후에 합리화한 문장처럼 느껴졌다. 좋아요 버튼이 로딩 중이면 당연히 막혀야 하는 거 아닌가 싶었다.

소스코드를 열어봤다. `ReactionButton`은 내부적으로 `TogglePrimitive.Root`와 `usePendingButton`을 조합한다. `useToggle.ts`에서 클릭 핸들러를 직접 찾아봤다.

```ts
onClick() {
  if (props.disabled) return;
  toggle();
}
```

`disabled`만 체크한다. `loading` 상태인지는 전혀 보지 않는다. `usePendingButton`이 하는 일을 보면 더 명확해진다.

```ts
export function usePendingButton(props: UsePendingButtonProps) {
  const { loading, disabled } = props;
  const stateProps = elementProps({
    "data-loading": loading ? "" : undefined,
    "data-disabled": disabled ? "" : undefined,
  });
  return { loading, disabled, stateProps };
}
```

`loading`은 `data-loading` attribute를 붙여서 CSS가 스피너를 보여주게 한다. 그게 전부다. 클릭 이벤트 흐름에는 아무 영향이 없다. `loading`과 `disabled`는 완전히 독립적인 두 개의 관심사로 구현되어 있다.

세 가지 가설을 세웠다. 첫째, 구현 미흡이다. 빠뜨렸을 뿐이고 문서는 사후 합리화다. 둘째, 취소 가능성 보존이다. 로딩 중 같은 버튼을 다시 누르면 취소 신호로 쓸 수 있게 한다. 셋째, 낙관적 업데이트 패턴과의 정합성이다.

첫째 가설은 탈락했다. `@seed-design/react`, `@seed-design/css`, `@seed-design/react-toggle`, `usePendingButton`까지 여러 패키지에 걸쳐 일관되게 같은 원칙이 적용되어 있다. 이건 실수가 반복된 것이 아니라 원칙을 반복한 것이다. `ActionButton`, `ContextualFloatingButton`, `ReactionButton` 모두 동일하다.

둘째 가설은 셋째와 양립하지만 단독으로는 약하다. 로딩 중 같은 버튼을 다시 눌러 취소 신호로 쓰는 동작은 결국 `pressed` 상태를 외부에서 토글하는 일이고, 이는 셋째 가설이 말하는 controlled component 구조 위에서만 성립한다. 즉 둘째는 셋째가 열어준 가능성의 한 사례일 뿐, 설계 의도를 따로 설명하는 독립 근거는 아니다.

셋째 가설이 가장 설득력 있다. `useToggle.ts`가 `useControllableState`를 써서 `pressed` 상태를 완전히 외부에서 제어 가능하게 만든 것이 결정적 증거다. 이 구조가 낙관적 업데이트를 위한 controlled component 패턴을 정확히 지원한다.

낙관적 업데이트는 이렇게 작동한다. 사용자가 좋아요 버튼을 누르는 순간 `pressed=true`와 `count + 1`을 로컬 상태에 즉시 반영한다. 그리고 서버 요청을 보낸다. 요청이 성공하면 `loading=false`로 바꾼다. 실패하면 `pressed=false`, `count - 1`로 롤백한다.

이 구간 동안 `loading=true`지만 사용자는 피드를 스크롤하며 다른 게시글 좋아요를 연달아 누를 수 있어야 한다. 만약 `loading`이 자동으로 `disabled`를 포함했다면, 컴포넌트를 재사용하는 모든 화면에서 "로딩 중에 다른 버튼도 막혀야 하는가"를 고려해야 한다. 그게 아무 문제가 없는 화면도 있고, 치명적인 UX 문제가 되는 화면도 있다.

소스코드를 더 파다가 흥미로운 것을 하나 더 발견했다. `useToggle.ts`가 HTML `disabled` attribute가 아니라 `aria-disabled`를 쓴다는 점이다.

```ts
rootProps: buttonProps({
  "aria-disabled": ariaAttr(props.disabled),
  onClick() {
    if (props.disabled) return;
    toggle();
  },
}),
```

HTML `disabled`와 `aria-disabled`는 다르다. HTML `disabled`는 버튼을 탭 순서에서 완전히 제거하고 클릭 이벤트를 브라우저 레벨에서 차단한다. 반면 `aria-disabled`는 스크린리더에 "이 버튼은 현재 비활성화 상태"라고 알려주되, 포커스와 클릭 이벤트는 살려둔다. 차이가 중요한 이유는 접근성에 있다. HTML `disabled`로 비활성화된 버튼은 키보드 탐색에서 아예 건너뛰어진다. 스크린리더 사용자는 그 버튼이 있다는 것조차 알 수 없다. `aria-disabled`를 쓰면 포커스를 받고 "왜 비활성화됐는지" 안내를 들을 수 있다. 당근 앱의 "주문하기" 버튼이 상품을 선택하지 않으면 비활성화될 때, 스크린리더 사용자가 버튼을 발견하고 "장바구니에 상품을 담아야 합니다"라는 맥락을 얻을 수 있어야 한다.

이 설계에는 해결되지 않은 트레이드오프도 있다. `loading ≠ disabled`를 허용하면 빠른 연타 시 race condition이 생긴다. 좋아요 → 취소 → 좋아요를 0.3초 안에 연타하면 서버 요청 세 개가 순서 없이 날아간다. 두 번째 응답이 세 번째보다 늦게 오면 서버 상태와 로컬 상태가 역전된다. 낙관적 업데이트의 구조적 약점이다. SEED Design은 이 문제를 컴포넌트에서 해결하지 않는다. debounce나 이전 요청 cancellation은 앱 레이어의 책임이다. "컴포넌트가 결정을 내리지 않는다"는 원칙의 그림자 같은 부분이다. 자유도를 주는 대신 그 자유도가 만들어내는 문제도 앱이 처리해야 한다.

이 설계에서 당근의 일관된 철학 하나를 발견했다. `loading`은 "지금 비동기 작업이 진행 중이다"라는 시각적 정보다. "그래서 클릭을 막아야 한다"는 판단은 비즈니스 로직이고, 그 판단은 사용하는 쪽이 한다. 컴포넌트는 정보를 전달할 뿐이고, 결정은 앱이 내린다.


## 아래로 당기기가 항상 새로고침이 아닌 이유

`PullToRefresh`에 `preventPull`이라는 prop이 있다. 특정 DOM 영역에서 PTR 제스처를 막는다. 왜 특정 영역에서만 막아야 하는가.

세 가지 가설을 세웠다. 내부에 스크롤 가능한 컴포넌트가 있어서 충돌한다. 텍스트 선택 제스처와 충돌한다. 슬라이더나 가로 스크롤 컨트롤과 충돌한다.

세 가설 모두 실제 상황이지만, 당근 앱에서 가장 빈번하게 발생하는 것은 텍스트 선택 충돌이다. 게시글 본문에서 주소나 가격을 드래그해서 복사하려는 경우가 있다. 웹뷰에서 `user-select: none`으로 텍스트 선택을 아예 막으면 UX가 나빠지고, 그렇다고 허용하면 아래로 드래그하는 순간 PTR이 발동된다. `preventPull`은 이 충돌을 컴포넌트 레벨에서 해소한다. 특정 영역에서만 PTR을 거부할 수 있으니, 텍스트가 있는 곳은 `preventPull`, 피드 빈 공간은 PTR이 작동하도록 구성할 수 있다.

`onPtrRefresh`가 `Promise`를 반환받는 설계도 생각해봤다. PTR 인디케이터는 `Promise`가 resolve될 때까지 계속 돌아간다. API 응답 전에 스피너가 먼저 꺼지면 "새로고침이 됐나, 아직인가"를 알 수 없다. 인디케이터의 소멸 자체가 데이터 갱신 완료의 신호다. 이것도 컴포넌트가 스스로 판단하지 않고 비동기 흐름의 완료 시점을 호출한 쪽이 알려주는 방식이다.


## 스크롤 가능 여부는 항상 보여야 한다

`ScrollFog`는 스크롤 위치를 추적하지 않는다. 끝까지 스크롤해도 fog가 사라지지 않는다. 처음엔 설계 실수처럼 보였다. "끝에 다 왔는데 왜 fog가 남아있지?"라고 생각했다.

가설이 두 갈래였다. 하나는 구현 단순성이다. 스크롤 이벤트 리스너 없이 CSS gradient만으로 만들어서 가볍다. 다른 하나는 사전 안내다. "더 있다"는 힌트는 스크롤하기 전에 필요하다. 끝에 다 왔을 때 fog가 사라지는 것은 사후 확인이지 사전 안내가 아니다.

문서에 이런 설명이 있었다. "scroll-fog는 scroll hint에 집중한 단순한 컴포넌트다." 기능 범위를 의도적으로 좁혔다는 명시적 선언이다. Chakra UI의 ScrollArea처럼 스크롤바 커스텀, 위치 감지, 섀도우 변화까지 다 하면 번들 크기가 커지고 웹뷰에서 무거워진다. 당근 앱의 카테고리 필터나 동네 칩 탭에서 "오른쪽에 더 있어요"를 알려주는 게 목적이라면 항상 보이는 fog가 오히려 올바르다.

패딩 요구사항이 스펙에 명시된 것도 흥미로웠다. 하단 80px, 좌우 20px 이상 패딩을 줘야 fog가 마지막 콘텐츠를 가리지 않는다. 이 요구사항이 없으면 개발자마다 다른 값을 쓰게 되고 마지막 아이템이 잘리는 버그가 팀마다 반복된다. 컴포넌트 스펙에 레이아웃 요구사항을 박아두는 것이 팀 간 불일치를 막는 방법이다.


## 드래그와 스크롤이 충돌할 때

`BottomSheet`에 `handleOnly` prop이 있다. true로 설정하면 핸들 영역만 시트를 드래그할 수 있고, 나머지 영역에서의 드래그는 내부 스크롤로 처리된다.

당근 앱의 지도 + 목록 화면을 생각해봤다. 지도 위에 목록이 담긴 시트가 올라와 있다. 목록을 아래로 스크롤하다가 시트가 닫혀버리면 사용자가 보던 맥락이 사라진다. `handleOnly`가 없으면 Vaul 라이브러리의 기본 동작은 콘텐츠 상단에서 추가 스크롤을 시트 드래그로 해석한다. 목록 최상단에서 조금만 더 올리면 시트가 줄어들거나 닫힌다.

`onOpenChange`가 닫힌 이유를 `"drag"`, `"closeButton"`, `"escapeKeyDown"`으로 구분해서 전달하는 것도 주목했다. 닫힌 방식이 다르면 사용자 의도가 다르다는 판단이 내포되어 있다. 드래그로 닫았다면 "지금은 보기 싫다"는 의도고, 버튼으로 닫았다면 "확인했고 명시적으로 종료한다"는 의도다. 이 정보로 analytics를 다르게 보내거나, 다시 열었을 때 상태를 다르게 복원하는 결정을 앱이 내릴 수 있다. `BottomSheetContent`가 `layerIndex`를 `--layer-index` CSS 변수로 받는 것도 시트가 시트 위에 열리는 케이스, 예를 들어 신고 플로우에서 확인 시트가 추가로 열리는 경우를 위해서다.


## 스낵바가 버튼을 가리면 안 된다

`Snackbar`의 `SnackbarAvoidOverlap`이 당근 앱 하단 구조의 복잡함을 드러낸다. 당근 앱에는 하단 탭바가 있고, 화면에 따라 글쓰기 FAB도 있다. 스낵바가 아무 위치에나 나오면 탭바를 가리거나 FAB 아래에 숨는다. `AvoidOverlap`을 쓰면 이런 요소들을 피해서 스낵바 위치가 자동으로 조정된다. 화면이 수십 개인 앱에서 스낵바 bottom 값을 각 화면마다 수동으로 계산하는 것은 유지보수 지옥이다.

`pauseOnInteraction`이 v0.1.14에서 기본값이 false에서 true로 바뀐 것도 눈에 띄었다. 이건 설계 변경이 아니라 실제 사용에서 발견한 문제를 고친 것이다. 사용자가 스낵바를 읽으려고 화면에 손을 올리는 순간 스낵바가 사라지는 버그를 겪었을 것이다. 짧은 타임아웃과 빠른 interaction이 겹치면 메시지를 놓친다. 기본값을 true로 바꾸는 것만으로도 사용자 경험이 달라진다. 문서에 버전을 명시한 것은 "우리가 이 문제를 겪었고 고쳤다"는 기록이기도 하다.

`strategy` prop이 `"immediate"`와 `"queued"` 두 가지인 것도 당근 앱 사용 패턴에서 나왔을 것 같다. 좋아요, 저장, 채팅 보내기를 연달아 하면 스낵바 세 개가 쌓인다. 동시에 세 개가 뜨면 읽을 수가 없다. `queued`는 하나씩 순서대로 보여주고, `immediate`는 최신 것으로 교체한다. 연속 행동의 결과를 쌓아서 보여줄 것인가, 최신 상태만 알려줄 것인가는 비즈니스 맥락에 따라 다르다. 이 판단도 컴포넌트 바깥으로 뺐다.


## 코치마크와 툴팁이 같은 컴포넌트일 수 없는 이유

`HelpBubble`에는 `HelpBubbleTrigger`와 `HelpBubbleAnchor` 두 가지가 있다. 처음에는 왜 하나로 통합하지 않는지 이해가 안 됐다. props로 구분하면 안 되나 싶었다.

생각해보니 두 컴포넌트는 인터랙션 모델 자체가 다르다. Trigger는 children 클릭으로 열고 닫는다. 열리는 트리거가 컴포넌트 안에 있다. Anchor는 children이 위치 지정만 하고, `open` 상태는 바깥에서 제어한다. 열리는 트리거가 컴포넌트 바깥에 있다.

당근 앱의 두 케이스를 대응시켜봤다. 각 화면의 물음표 버튼 옆 설명 툴팁은 Trigger다. 사용자가 눌러야 열린다. 반면 신기능 온보딩 코치마크는 Anchor다. 당근페이 처음 사용하는 사람에게 결제 버튼 옆에 자동으로 안내 버블을 보여줘야 한다면, 사용자가 아무것도 하지 않아도 열려야 한다. 그 열림의 트리거는 "처음 결제 화면에 진입했다"는 앱 상태고, 그 상태를 관리하는 건 컴포넌트 바깥이다.

두 컴포넌트가 `HelpBubble` 네임스페이스 안에 있다는 것도 의미가 있다. 시각적으로는 같은 버블이다. 렌더링 로직을 공유하면서 인터랙션 진입 방식만 다르게 만든 것이다. 하나의 컴포넌트에 `triggerMode: "click" | "auto"` 같은 prop을 추가했다면, auto 모드일 때 click 관련 props들이 불필요하게 노출된다. 컴포넌트를 나누면 인터페이스가 더 명확해진다.


## 패턴들에서 반복되는 하나의 원칙

여섯 가지 패턴을 분석하고 나서 공통점 하나가 보였다. 컴포넌트가 결정을 내리지 않는다.

`loading ≠ disabled`는 클릭 허용 여부를 앱에 맡긴다. ScrollFog는 스크롤 위치 판단을 하지 않는다. BottomSheet의 `handleOnly`는 드래그 영역을 선택하게 한다. Snackbar의 `strategy`는 표시 전략을 고르게 한다. HelpBubble은 열리는 트리거를 분리한다. PullToRefresh의 `preventPull`은 제스처 허용 영역을 앱이 정하게 한다.

당근이 디자인 시스템을 만들면서 반복적으로 마주친 질문이 "이 판단은 컴포넌트가 해야 하는가, 앱이 해야 하는가"였을 것이다. 그리고 그 답이 일관되게 "앱이 한다"로 수렴했다. 컴포넌트는 표현과 접근성과 애니메이션을 책임진다. 언제, 어떻게, 왜 그 컴포넌트가 동작할지는 앱이 결정한다.

이것이 좋은 디자인 시스템과 나쁜 디자인 시스템의 차이라고 생각했다. 결정을 너무 많이 내리는 컴포넌트는 처음엔 편하지만 맥락이 달라지면 우회할 방법이 없다. 결정을 앱에 미루는 컴포넌트는 처음엔 조금 더 많이 써야 하지만, 어떤 맥락에서도 원하는 대로 쓸 수 있다. 당근 앱처럼 수십 개 팀이 수백 개 화면을 만드는 환경에서는 후자가 훨씬 중요하다.
